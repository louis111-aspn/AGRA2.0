01 · FIORI 개발 아키텍처 기초
SAP Fiori 앱은 브라우저에서 실행되는 화면(SAPUI5)과 S/4HANA 내부의 데이터·로직(RAP Business Object)이 OData라는 표준 규격을 통해 완전히 분리되어 통신하는 구조이며, 본 프로젝트의 모든 파일은 이 4단 구조(화면 · 데이터 계약 · 백엔드 로직 · 실행 환경) 중 하나의 역할만을 담당함

소스 코드 분석에 들어가기 전, SAP Fiori 개발을 처음 접하는 경우를 가정해 프로젝트 전체를 관통하는 기본 개념을 먼저 정리합니다. 이 챕터의 용어와 계층 구조를 이해하면 이후 챕터의 파일별 설명이 "왜 그렇게 나뉘어 있는지"까지 자연스럽게 연결됩니다.

① SAP Fiori와 SAPUI5는 무엇인가

SAP Fiori는 SAP가 제공하는 업무용 앱의 디자인 원칙이자 앱 모음의 이름이고, SAPUI5(UI5)는 그 디자인을 실제로 구현하는 자바스크립트 프레임워크입니다. 일반 웹 개발에 비유하면 React·Vue와 같은 위치에 있는 프레임워크로, 이 프로젝트의 webapp/ 폴더 전체가 UI5로 작성된 하나의 "화면 앱(브라우저에서 실행되는 부분)"입니다. 화면 앱은 S/4HANA 시스템 자체가 아니라, S/4HANA가 노출한 데이터 창구(OData)에 접속하는 별도의 클라이언트 프로그램입니다.

② 화면 앱 내부 구조 — MVC 패턴

UI5 앱은 예외 없이 아래 3가지 역할로 파일이 나뉩니다. 이 프로젝트의 view/, controller/, model/ 폴더명이 그대로 이 역할을 의미합니다.

VIEW

화면 (.view.xml)

버튼, 입력창, 테이블 등 사용자가 눈으로 보는 레이아웃만 XML로 선언. 로직은 포함하지 않음. 예: Main.view.xml

CONTROLLER

로직 (.controller.ts)

버튼 클릭·파일 선택 등 이벤트가 발생했을 때 실행되는 실제 코드. 예: Main.controller.ts

MODEL

데이터 (JSONModel / ODataModel)

화면과 로직이 공유하는 데이터 저장소. 화면 임시 상태용 JSONModel과, 서버 데이터용 ODataModel 두 종류가 함께 쓰임

View와 Controller는 controllerName 속성으로 1:1 연결되고, Model은 setModel(모델, "이름")으로 View에 이름표를 달아 바인딩됩니다. 이 프로젝트에서 objectView라는 이름의 JSONModel이 반복적으로 등장하는 이유가 여기에 있습니다 — 화면 전용 임시 데이터(업로드 파일명, 처리 중 여부, 결과 메시지 등)를 담는 그릇의 이름입니다.

③ 앱의 시작점 — Component와 manifest

Component.ts

앱의 진입점(부트스트랩)

브라우저가 앱을 켤 때 가장 먼저 실행되는 코드. "어떤 화면부터 보여줄지" 라우터를 초기화하는 역할만 수행 — 일반 웹 프레임워크의 main.js/App.tsx에 해당

manifest.json

앱의 설정 명세서

이 앱이 어떤 데이터 서비스에 붙는지(dataSources), 화면이 몇 개고 어떤 순서로 전환되는지(routing), Fiori 홈 화면에 어떻게 등록되는지(crossNavigation)를 코드가 아닌 선언적 설정으로 기술

④ 화면과 서버를 잇는 통로 — OData

이 화면 앱은 S/4HANA 데이터베이스에 직접 접속하지 않습니다. 대신 OData라는 REST 기반 표준 규격을 통해 서버와 통신합니다. OData는 "이 서비스에는 어떤 데이터 항목(Entity)이 있고, 어떤 함수(Function Import)를 호출할 수 있는지"를 메타데이터라는 계약서로 미리 정의해 둔 것이 특징입니다. 이 프로젝트의 localService/metadata.xml이 바로 그 계약서의 로컬 사본이며, 프런트엔드 코드는 이 계약서에 정의된 이름(Bulk_Import_and_Update 등)만 호출할 수 있고 그 내부 구현은 알지 못한 채로 동작합니다.

⑤ 서버 쪽 구조 — RAP와 클린 코어(Clean Core)

OData 서비스 뒤편에서 실제 데이터 처리를 담당하는 것이 RAP(RESTful ABAP Programming)로 작성된 Business Object(BO)입니다. S/4HANA Public Cloud는 원칙적으로 SAP가 제공한 표준 프로그램(코어)을 고객이 직접 수정할 수 없습니다 — 이를 클린 코어(Clean Core) 원칙이라 부릅니다. 대신 RAP로 별도의 확장 프로그램(BO)을 새로 만들고, 이 BO를 OData로 노출해 화면 앱과 연결하는 방식으로 "코어를 건드리지 않고 기능을 추가"합니다. 이 프로젝트의 ZSD_GRVUPL BO가 바로 그 확장 프로그램이며, 메타데이터에 보이는 Draft 관련 엔티티(I_DraftAdministrativeDataType 등)는 RAP가 표준적으로 제공하는 "임시 저장(초안) 편집" 기능의 흔적입니다.

⑥ 화면 전환과 앱 간 이동 — 라우팅과 FLP

한 앱 내부의 화면 전환은 Router가 담당하고(manifest.json의 routing에 정의), 서로 다른 앱 사이의 이동은 Fiori Launchpad(FLP)라는 SAP의 통합 포털이 담당합니다. 앱마다 Semantic Object와 Action이라는 두 개의 이름표가 붙는데, 이는 URL의 도메인/경로와 비슷한 개념으로 "이 앱을 무엇이라 부르고 어떤 동작인지"를 표시합니다. 이 프로젝트가 처리 완료 후 PG_DC_0020/002로 이동하는 것은, "PG_DC_0020이라는 이름의 다음 모듈 앱을 열어달라"고 FLP에 요청하는 것과 같습니다.

⑦ 개발 · 빌드 · 배포 파이프라인

같은 소스 코드가 상황에 따라 다른 방식으로 실행됩니다. 개발 중에는 ui5.yaml이 실제 SAP 서버에 프록시로 연결해 실시간 확인을, ui5-mock.yaml은 가짜 데이터로 오프라인 개발을, 최종적으로 ui5-deploy.yaml은 완성된 코드를 SAP 서버 내부의 저장 공간(ABAP Repository, 흔히 BSP라 부름)으로 업로드합니다. TypeScript로 작성된 코드는 배포 전 UI5가 이해하는 JavaScript로 자동 변환(transpile)되는데, 이는 사람이 보기 편한 TS 문법과 브라우저가 실행하는 JS 문법을 분리하기 위함입니다.

02 · PROJECT OVERVIEW & ARCHITECTURE
본 프로젝트는 SAP Fiori 표준 도구로 생성된 Freestyle 앱으로, 클린 코어 원칙에 따라 S/4HANA 코어를 수정하지 않고 별도 OData 서비스·RAP Unbound Action을 통해 Non-SAP 법인의 시산표 데이터를 GR 시스템에 반영함

2025년 3월 SAP Fiori Tools App Generator(Simple 템플릿)로 생성되었으며, TypeScript + UI5 1.130.7 조합으로 구축되었습니다. 백엔드는 RAP(RESTful ABAP Programming) 기반 Draft-enabled Business Object ZSD_GRVUPL이며, 프런트엔드는 이 BO를 노출하는 OData V2 서비스 ZSB_GRVUPL을 단일 데이터 소스로 사용합니다.

#항목내용 및 조치 방향
1RBUPTR 리네이밍 롤백(정상)커밋 메시지에는 RBUPTR 반영으로 기록되어 있으나, 실제로는 전송 로직 구현이 이루어지지 않아 PRBUPTR로 의도적으로 원상복구된 상태. 코드는 정상이며, 커밋 메시지와 실제 반영 범위가 달라 향후 이력 추적 시 혼선의 소지가 있으므로 커밋 설명 보완을 권장
2미완성 화면 공존TemplateDownloadScreen 관련 View/Controller가 스텁 상태로 라우팅에만 등록되어 있음. 완성하거나 라우트·번들에서 제거하는 결정 필요
3하드코딩 템플릿 GUID템플릿 다운로드 로직의 templateId가 소스에 고정값으로 박혀 있어 템플릿 갱신 시 다운로드가 깨질 수 있음
4디버그 잔재MessageBox.information("여기로 오나요?") 등 개발 중 확인용 코드가 운영 코드에 잔존 — 클린업 필요
5대량 데이터 처리 구조행 수만큼 개별 callFunction Promise를 생성 후 단일 배치 커밋하는 구조로, 수백~수천 행 규모에서는 청크 분할 전송 여부 검토 권장
6Draft 인프라와 실사용 패턴의 괴리메타데이터상 Draft 표준 액션이 다수 정의되어 있으나 프런트는 Unbound Function 하나로 전량 처리 — BO 설계와 UI 사용 패턴 정합성 재검토 여지
